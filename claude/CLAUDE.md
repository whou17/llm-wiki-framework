# LLM Wiki 总控工作指引

**版本**: v5.16 (2026-06-07)
**项目**: LLM 驱动的知识库管理框架
**引擎**: Claude Code (Claude Agent SDK)

---

## 核心原则

> **标签是地基，进出有记录**

本文件是 LLM 的总控工作指引。它定义了三个核心工作流（摄入、检索、健康检查）的触发词和执行步骤，确保 LLM 按照标准化流程操作知识库。

---

## 一、触发词与执行入口

| 触发词 | 执行脚本 | 说明 |
|--------|---------|------|
| "同步检测" | `python3 claude/sync-log.py` | 检测 raw/ 新增/删除/空壳文件 |
| "学习新增" | → 执行 Knowledge-IN 流程 | 摄入新文章 |
| "查/调取/关于" | → 执行 Knowledge-OUT 流程 | 调取已有知识 |
| "健康检查" | → 执行 Knowledge-LINT 流程 | 矛盾/时效/孤立/缺口检测 |

## 二、Knowledge-IN 流程（学习入库）

**触发词**: "学习"、"提炼"、"入库"

> **核心设计**：每一步的完成标准内嵌在步骤自身中，不设事后检查环节。

```
[Step 1] 文件诊断 ← 每个待学习文件必须得出以下诊断结果之一
   ├─ 运行: python3 claude/sync-log.py
   ├─ 对每个新文件判定状态：
   │   ├─ 🔴 非 md 格式（.docx/.doc/.pdf）→ 进入 Step 2-A
   │   ├─ 🔴 链接壳（.md 正文 ≤3 行且仅含 URL）→ 进入 Step 2-B
   │   ├─ 🟡 疑似图片型（标题含"一图读懂"、或正文 <5 行且含图片链接）→ 进入 Step 2-C
   │   └─ 🟢 正常 md（正文 ≥5 行有实质内容）→ 直接进入 Step 3
   │
   │   ⚠ 此步骤不可跳过：每个文件必须有诊断标签才能继续

[Step 2-A] 格式转换（非 md → md）
   ├─ .docx/.doc: textutil -convert txt → 重命名为 .md
   ├─ .pdf: python3 -c "import pdfplumber..." 提取文字 → 保存为同名 .md
   ├─ 转换完成后删除原文件
   └─ ✅ 完成标准：同名 .md 存在且 ≥5 行正文

[Step 2-B] 链接提取（defuddle）
   ├─ defuddle parse <URL> --md -o <file>
   ├─ ✅ 完成标准：defuddle 返回码 = 0 且输出文件 ≥5 行正文
   ├─ ❌ 不满足 → 换 WebSearch 搜索文章标题补充内容后写入
   ├─ ⛔ 提取成功后必须删除原链接壳 .md 文件（避免空壳残留）
   └─ 💡 常见失败：微信公众号验证墙 → 直接走 WebSearch 备用方案

[Step 2-C] 图片文字提取（OCR）
   ├─ 下载图片 → 若高度 >3000px 用 Pillow 拆分为多个 chunk
   ├─ macOS: 编译 swift 脚本调用 Vision 框架逐 chunk OCR
   ├─ 整合 OCR 结果 → 整理为结构化 markdown → 写入文件
   ├─ ⛔ 提取完成后必须删除原始图片文件
   └─ ✅ 完成标准：输出文件 ≥10 行正文

[Step 3] 讨论确认 ← 每个待学习文件
   ├─ AI 列出核心要点（3-5条）
   └─ 用户确认或调整重点方向

[Step 4] 提取 — 按文件类型选方法（见 schema/3.learning-methods.md 第一篇）
   ├─ 政策类 → 政策学习法（5步：抓总→拆块→提炼→主要精华→行动清单）
   │   └─ ⭐ 必须收录"把...作为..."等制度定位句式（原文照录+条文编号）
   ├─ 典型案例 → 案例拆解法（四问+双写）
   └─ 学术文章 → 观点萃取法（3步：观点→论据→趋势信号）

[Step 5] 存储 — 写入知识库（见 schema/3.learning-methods.md 第二篇）
   ├─ 上级政策/案例/学术 → wiki/concepts/ 或 wiki/entities/
   ├─ 本校文件 → 三层分流（稳定层/年度层/事件层）
   └─ ✅ 完成标准：wiki 目标文件中出现本次新增的章节/板块内容
       ├─ ⛔ 禁止用"更新 source 列表"替代"内容入库"
       └─ ⛔ 必须在写入时即确认 wiki 文件已更新，不得事后补查

[Step 6] 更新记录
   ├─ frontmatter: source 置顶 + last-updated 更新
   └─ sync-log.py 自动处理
```

## 三、Knowledge-OUT 流程（知识点调用）

**触发词**: "查"、"调取"、"关于XXX"

```
[Step 1] 解析需求
   └─ 提取主题/关键词

[Step 2] 检索知识库
   └─ Grep 搜索 wiki/ 相关文件

[Step 3] 输出结果
   ├─ 核心要点提炼
   ├─ 标注来源文件
   └─ 标注置信度

[Step 4] 回写保存
   ├─ 查询结果是否有跨领域发现或综合分析价值？
   └─ 是 → 写入 wiki/synthesis/，更新 index.md
```

## 三-A、Knowledge-LINT 流程（健康检查）

**触发词**: "健康检查"、"查矛盾"、"查遗漏"

```
[Step 1] 矛盾检测
   └─ 搜索不同来源对同一主题的冲突主张，标注在 contradictions 字段

[Step 2] 时效检测
   └─ 检查 last-updated 超过 60 天的页面，对照最新来源是否有过时内容

[Step 3] 孤立检测
   └─ 搜索无入链的页面（Grep 全库确认无其他页面引用）

[Step 4] 缺口检测
   └─ 识别重要但缺失的概念页，建议新建

[Step 5] 输出健康报告
   ├─ 问题清单 + 建议优先级
   └─ 用户确认后执行修复
```

## 四、禁止事项（核心）

```
❌ 捏造标签（必须用 tag-index.md 中的标签）
❌ 简化政策表述（原文引用，不失真）
❌ 删除原文已有内容
❌ "幻想"（捏造不在原文中的表述）
❌ 表格输出文字材料
```

---

## 四-A、标签管理

**铁律**: 标签必须来自 `schema/2.tag-index-template.md`（或用户自定义的标签字典），禁止捏造。

**同步规则**: 标签字典与 `wiki/concepts/` 保持双向一致：
- 标签字典新增或变更标签后，检查 concept 页面是否有遗留标签需替换
- concept 页面使用新标签时，确认其已在标签字典中注册
- 每次健康检查需验证 concept 标签与标签字典的对齐状态

**增长**: 摄入时如现有标签无法覆盖，在页面 `open-questions` 提案：
```
  - "tag-proposal: #新标签名 | 说明 | 理由：现有[X]无法覆盖[场景]"
```
→ 用户采纳后更新标签字典 + 版本号。

## 五、准确保障

**入库前核查清单**:
```
□ 原文表述完整保留？
□ 任务编号/序号准确？
□ 牵头单位/责任单位标注？
□ 数据指标原文照录？
□ 来源文件路径正确？
□ "把...作为..."等制度定位句式原文收录（附条文编号）？
□ 无"幻想"内容？
```

## 七、日志与页面维护

### log.md 按月归档
- log.md 仅保留当月记录
- 每月1日（或月初首次操作），将上月内容移至 `wiki/log-YYYY-MM.md`
- 归档格式：保留原 `## [日期]` 标题结构

### 单页面大小限制
- 软上限：300 行
- 超过时：拆分为子页面，主页面保留概述 + `[[子页面]]` 链接

### index.md 自动维护
- 每次摄入后更新 index.md 的"更新时间"和统计数字
- 每次新建/删除 wiki 页面后更新对应表格

### source 去重
- 摄入前检查目标页面的 source 列表
- 已存在的来源不重复添加（更新位置置顶即可）
