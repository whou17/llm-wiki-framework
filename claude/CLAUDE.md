## 核心原则

> **标签是地基，进出有记录。优先级决定执行，闸门保证质量。**

## 〇、指令优先级体系

> **设计原则**：不是所有规则同等重要。优先级告诉模型"违反哪一个更严重"。
> **启发来源**：Claude Fable 5 的 `NON-NEGOTIABLE` / `SEVERE VIOLATION` / `CRITICAL` 标记系统。

| 层级 | 标记 | 含义 | 违反后果 |
|------|------|------|---------|
| 🔴 L1-硬限制 | `HARD LIMIT` | 绝对不可违反 | 结果作废，需重做 |
| 🟠 L2-关键 | `CRITICAL` | 必须执行，不可跳过 | 结果质量严重下降 |
| 🟡 L3-重要 | `IMPORTANT` | 应执行，例外需主动说明 | 结果质量部分下降 |
| 🟢 L4-指南 | `GUIDELINE` | 建议遵循，可弹性调整 | 可接受但非最优 |

### L1-硬限制

- `HARD LIMIT` ❌ 捏造不在 `schema/2.tag-index.md` 中的标签
- `HARD LIMIT` ❌ "幻想"（捏造不在原文中的表述）
- `HARD LIMIT` ❌ 用"更新 source 列表"替代"内容入库"
- `HARD LIMIT` ❌ 简化政策表述（制度定位句式必须原文照录）
- `HARD LIMIT` ❌ 删除原文已有内容

### L2-关键

- `CRITICAL` Step 1 文件诊断不可跳过：每个文件必须有诊断标签
- `CRITICAL` 写入 wiki 前必须先 Read 目标文件的最新内容
- `CRITICAL` 制度定位句式（"把...作为..."等）必须原文照录+条文编号
- `CRITICAL` 执行任何步骤前，必须先确认是否需要读取关联 schema 文件
- `CRITICAL` sync-log.py 运行结果必须逐一处理，不得批量跳过

### L3-重要

- `IMPORTANT` 每个 source 文件的内容必须实际写入 wiki 页面
- `IMPORTANT` source 去重：已存在的来源不重复添加
- `IMPORTANT` 标签双向一致：tag-index ↔ wiki/concepts/

### L4-指南

- `GUIDELINE` 单页面软上限 300 行，超过时拆分子页面
- `GUIDELINE` 摄入时如现有标签无法覆盖，在页面 `open-questions` 提案新标签

## 〇-A、模型能力边界

> **设计原则**：明确告诉模型它知道什么、不知道什么，减少过度自信和过度保守。

### 模型已知能力
- 可以直接读取和编辑 `raw/`、`wiki/`、`schema/` 下的所有文件
- 可以运行 `claude/sync-log.py` 进行增量检测
- 可以 Grep 全库搜索关键词

### 模型已知局限
- **不知道 wiki/ 中某个页面的最新内容** → 必须先 Read 再操作，不可凭记忆
- **不知道 raw/ 中是否有新文件** → 必须先运行 sync-log.py
- **不知道两个概念页之间是否存在矛盾** → 需 Grep 全库对比
- **标签合法性只能通过读取 tag-index.md 验证** → 不可凭记忆判断标签是否存在
- **不知道 wiki 页面是否已被他人修改** → 写入前必须 Read 最新版本

### 知识库覆盖范围
- 概念页：`wiki/concepts/` 目录（Grep 可查）
- 实体页：`wiki/entities/` 目录
- 综合产出：`wiki/synthesis/` 目录
- 标签体系：`schema/2.tag-index.md`
- 操作日志：`wiki/log.md`

|--------|---------|------|

## 一-A、任务复杂度与执行深度 `IMPORTANT`

> **设计原则**：根据任务规模自动缩放执行深度，避免"杀鸡用牛刀"或"大题小做"。

| 规模 | 触发条件 | 执行深度 |
|------|---------|---------|
| **S-简单** | 查询单个已知概念 / 事实 | 直接 Grep + 输出，不启动完整 Knowledge-OUT |
| **M-标准** | 摄入 1-3 个新文件 | Knowledge-IN 完整 6 步，每文件独立 |
| **L-批量** | 摄入 4-10 个新文件 | 每文件独立 6 步，Step 3（讨论确认）可合并汇报 |
| **XL-大规模** | 摄入 10+ 个新文件 | 先 sync-log → 按文件类型分组 → 分批执行，每批完成后汇报进度 |

## 二、Knowledge-IN 流程（学习入库）

**触发词**: "学习"、"提炼"、"入库"

> **核心设计**：每一步的完成标准内嵌在步骤自身中，不设事后检查环节。关键步骤设有**执行前自检闸门**。

```
[Step 1] 文件诊断 ← 每个待学习文件必须得出以下诊断结果之一 `CRITICAL`
   ├─ 运行: python3 claude/sync-log.py
   ├─ 对每个新文件判定状态：
   │   ├─ 🔴 非 md 格式（.docx/.doc/.pdf）→ 进入 Step 2-A
   │   ├─ 🔴 链接壳（.md 正文 ≤3 行且仅含 URL）→ 进入 Step 2-B
   │   ├─ 🟡 疑似图片型（标题含"一图读懂"、或正文 <5 行且含图片链接）→ 进入 Step 2-C
   │   └─ 🟢 正常 md（正文 ≥5 行有实质内容）→ 直接进入 Step 3
   │
   │   ⚠ 此步骤不可跳过：每个文件必须有诊断标签才能继续

[Step 2-A] 格式转换（非 md → md）
   ├─ .docx/.doc: textutil -convert txt → 重命名为 .md
   │   └─ 降级方案：textutil 不可用 → pandoc --to=markdown
   ├─ .pdf: python3 -c "import pdfplumber..." 提取文字 → 保存为同名 .md
   │   └─ 降级方案：pdfplumber 无文字层（扫描件）→ 进入 Step 2-C OCR 流程
   ├─ 转换完成后删除原文件
   └─ ✅ 完成标准：同名 .md 存在且 ≥5 行正文

[Step 2-B] 链接提取（defuddle）
   ├─ defuddle parse <URL> --md -o <file>
   ├─ ✅ 完成标准：defuddle 返回码 = 0 且输出文件 ≥5 行正文
   ├─ ❌ 不满足 → 换 WebSearch 搜索文章标题补充内容后写入
   ├─ ⛔ 提取成功后必须删除原链接壳 .md 文件（避免空壳残留）
   └─ 💡 常见失败：微信公众号验证墙 → 直接走 WebSearch 备用方案

[Step 2-C] 图片文字提取（OCR）
   ├─ 下载图片 → 若高度 >3000px 用 Pillow 拆分为多个 chunk
   ├─ macOS: 编译 swift 脚本调用 Vision 框架逐 chunk OCR
   ├─ 整合 OCR 结果 → 整理为结构化 markdown → 写入文件
   ├─ ⛔ 提取完成后必须删除原始图片文件
   ├─ ❌ 降级方案：图片质量过低导致 OCR 失败 → 标记为"待人工处理"，不删除原文件
   └─ ✅ 完成标准：输出文件 ≥10 行正文

[Step 3] 讨论确认 ← 每个待学习文件 `IMPORTANT`
   ├─ AI 列出核心要点（3-5条）
   └─ 用户确认或调整重点方向

[Step 4] 提取 — 按文件类型选方法（见 schema/3.learning-methods.md 第一篇）

   **执行前自检** `CRITICAL`：
   □ 已读取 schema/3.learning-methods.md？（不可凭记忆选方法）
   □ 文件类型识别正确？政策类/案例类/学术类三者互斥
   □ 制度定位句式已用正则（把.*作为、把.*放在、以.*为）全文检索？

   ├─ 政策类（含本校） → 政策学习法（5步：抓总→拆块→提炼→主要精华→行动清单）
   │   └─ ⭐ `HARD LIMIT` 必须收录"把...作为..."等制度定位句式（原文照录+条文编号）
   ├─ 典型案例 → 案例拆解法（四问+双写）
   └─ 学术文章 → 观点萃取法（3步：观点→论据→趋势信号）

[Step 5] 存储 — 写入知识库（见 schema/3.learning-methods.md 第二篇）

   **执行前自检** `CRITICAL` — 必须全部通过才能写入：
   □ 目标 wiki 文件已 Read 最新内容？（禁止凭记忆写入）
   □ 本次新增内容与已有内容不重复？
   □ source 列表已检查去重？
   □ 制度定位句式已原文照录（附条文编号）？
   □ 数据指标原文照录，未简化？
   □ 无"幻想"内容？
   → 全部通过 → 执行写入
   → 任一项未通过 → 修正后重新自检

   ├─ 上级政策/案例/学术 → wiki/concepts/ 或 wiki/entities/
   ├─ 本校文件 → 三层分流（稳定层/年度层/事件层）
   └─ ✅ 完成标准：wiki 目标文件中出现本次新增的章节/板块内容
       ├─ ⛔ `HARD LIMIT` 禁止用"更新 source 列表"替代"内容入库"
       └─ ⛔ `CRITICAL` 必须在写入时即确认 wiki 文件已更新，不得事后补查

[Step 6] 更新记录
   ├─ frontmatter: source 置顶 + last-updated 更新
   └─ sync-log.py 自动处理
```

## 二-A、降级路径总表 `IMPORTANT`

> **设计原则**：每一步的主方案可能失败，必须有预设的降级路径，避免流程卡死。

| 步骤 | 主方案 | 失败条件 | 降级方案 |
|------|--------|---------|---------|
| Step 2-A (docx→md) | `textutil -convert txt` | textutil 不可用 | `pandoc --to=markdown` |
| Step 2-A (pdf→md) | `pdfplumber` 提取文字 | 无文字层（扫描件） | 走 Step 2-C OCR 流程 |
| Step 2-B (链接→md) | `defuddle parse` | 验证墙 / 返回码≠0 | `WebSearch` 搜索文章标题补充内容 |
| Step 2-C (OCR) | Vision 框架逐 chunk OCR | 图片质量过低 | 标记"待人工处理"，保留原文件 |
| Step 4 (政策提取) | 5 步完整流程 | 文件过长(>500 行) | 抓总→拆块→选重点板块提炼，其余概述 |
| Step 4 (案例拆解) | 四问+双写 | 案例信息不全 | 已有信息正常提取，缺失字段标注"原文未提供" |
| Step 5 (存储) | 写入 wiki 目标文件 | 目标文件被锁定/不可写 | 先写入临时文件，通知用户手动合并 |
| 任意步骤 | AI 不确定操作是否正确 | 歧义无法自行解决 | 暂停并询问用户，不要猜测执行 |

## 三、Knowledge-OUT 流程（知识点调用）

**触发词**: "查"、"调取"、"关于XXX"

```
[Step 1] 解析需求
   └─ 提取主题/关键词

[Step 2] 检索知识库
   └─ Grep 搜索 wiki/ 相关文件

[Step 3] 输出结果
   ├─ 核心要点提炼
   ├─ 标注来源文件
   └─ 标注置信度

[Step 4] 回写保存 `IMPORTANT`
   ├─ 查询结果是否有跨领域发现或综合分析价值？
   └─ 是 → 写入 wiki/synthesis/，更新 index.md
   └─ 否 → 不执行回写（简单查询不需要写入）
```

## 三-A、Knowledge-LINT 流程（健康检查）

**触发词**: "健康检查"、"查矛盾"、"查遗漏"

```
[Step 1] 矛盾检测
   └─ 搜索不同来源对同一主题的冲突主张，标注在 contradictions 字段

[Step 2] 时效检测
   └─ 检查 last-updated 超过 60 天的页面，对照最新来源是否有过时内容

[Step 3] 孤立检测
   └─ 搜索无入链的页面（Grep 全库确认无其他页面引用）

[Step 4] 缺口检测
   └─ 识别重要但缺失的概念页，建议新建

[Step 5] 输出健康报告
   ├─ 问题清单 + 建议优先级
   └─ 用户确认后执行修复
```

## 四-A、标签管理

**铁律** `HARD LIMIT`: 标签必须来自 `schema/2.tag-index.md`，禁止捏造。

**同步规则** `IMPORTANT`: `schema/2.tag-index.md` 与 `wiki/concepts/` 保持双向一致：
- tag-index 新增或变更标签后，检查 concept 页面是否有遗留标签需替换
- concept 页面使用新标签时，确认其已在 tag-index 中注册
- 每次健康检查需验证 concept 标签与 tag-index 的对齐状态

**增长** `GUIDELINE`: 摄入时如现有标签无法覆盖，在页面 `open-questions` 提案：
```
  - "tag-proposal: #新标签名 | 说明 | 理由：现有[X]无法覆盖[场景]"
```
→ 用户采纳后更新 tag-index.md + 版本号。

## 四-B、Wiki 页面输出格式规范 `IMPORTANT`

> **设计原则**：wiki 知识库不是聊天记录，需要一致的格式规范确保可读性和可检索性。

### 何时使用 prose（自然段落）
- ✅ 概念解释、背景叙述、趋势分析 → 使用 prose
- ✅ 制度定位原文照录 → 使用 `> **（第X条）** ...` 引用块
- ✅ 每段 3-5 句，避免单句成段

### 何时使用列表
- ✅ 多项任务指标（序号+要点+责任单位+关键词）→ 使用表格
- ✅ 多条并列的制度定位 → 使用 `> **（第X条）** ...` 逐条列出
- ❌ 大段政策原文 → 禁止用表格呈现，用 prose + 关键句引用

### 何时使用表格
- ✅ 任务指标对照（序号+核心要点+责任单位+关键词）
- ✅ 三层分流对照（层级+目标文件+内容范围+更新频率）
- ✅ 降级路径对照（步骤+主方案+失败条件+降级方案）
- ❌ `HARD LIMIT` 禁止：用表格输出文字材料

### 板块标题规范
- 使用 `## 板块名`（二级标题）作为 wiki 页面的板块分隔
- 板块名优先使用原文中的概念，不自行发明
- 禁止使用 `**粗体**` 代替标题
- 板块顺序：制度定位 → 核心内容 → 行动/启示 → 来源

## 五、Policy-ORG 流程（制度文件梳理）

**触发词**: "制度梳理"、"整理制度"、"梳理制度"

> **适用场景**: raw/policy/ 下积累了未分类的大量制度文件，需要统一整理。

```
[Step 1] 文件扫描与完整性检查 `CRITICAL`
   ├─ 统计所有文件行数，标记短文件（<30 行）为待审核
   ├─ MD5 检测精确重复，标记完全相同的文件
   └─ 输出：文件总数、短文件列表、精确重复列表

[Step 2] 分类 `CRITICAL`
   ├─ 按关键词自动分类到五大类：
   │   ├─ 党建（组织、宣传、纪检、统战、思想政治、意识形态、干部管理）
   │   ├─ 科研（科技、创新、成果转化、产教融合、校企合作）
   │   ├─ 育人（教学、课程、学生、辅导员、就业、学科专业、师范认证）
   │   ├─ 综合（安全、法治、考核、人事、教师队伍、师德师风、综合改革）
   │   └─ 财务（国有资产、经费、金融）
   └─ 无法自动分类的归入"综合"，人工审核后调整

[Step 3] 去重 `IMPORTANT`
   ├─ 同一制度多个来源版本的，保留行数最多/最完整的版本
   ├─ 删除较短版本（标记后由用户确认）
   └─ 文件名含" 1"或"(1)"后缀的视为疑似重复，基础名存在则删除后缀版本

[Step 4] 识别机构内部文件 `IMPORTANT`
   ├─ 搜索文件内容和文件名中的机构关键词
   ├─ 确认后转存至 raw/documents/
   └─ 非政策类文件（新闻、评论、答记者问等）转存至 raw/sources/

[Step 5] 重命名 `CRITICAL`
   ├─ 格式：[类型]-[序号]-[文号]-[名称].md
   │   ├─ 类型：党建/科研/育人/综合/财务
   │   ├─ 序号：按年份由旧到新 01、02、03...
   │   ├─ 文号：提取原文号（如 国办发〔2017〕95号），无则标注"无文号"
   │   └─ 名称：清理前缀后缀后的核心文件名
   └─ 文号提取规则：
       ├─ 匹配 国办发/鲁政办字/鲁政发/鲁政字/教党/教高厅/鲁教... 等前缀
       ├─ 匹配 教育部令第X号/国务院令第X号
       └─ 匹配 中组发/鲁组发/鲁组字/鲁科字/鲁人社字/财资 等

[Step 6] 同步 `CRITICAL`
   ├─ 运行 sync-log.py 清理过期记录
   ├─ 将所有新路径标记为已学习（避免误判为新增）
   └─ 确认状态为"完全同步"
```

### 辅助脚本

`claude/policy-organize.py` 提供了上述流程的自动化支持：
- 自动分类（基于文件名关键词）
- 文号提取（正则匹配 20+ 种文号模式）
- 短名称清理（去除来源后缀、日期前缀、序号前缀）
- 生成重命名命令

## 六、准确保障

### 入库前核查清单（汇总）

> 以下核查点已嵌入各 Step 的执行前自检闸门中，此处为全局汇总，供最终确认。

```
□ L1 原文表述完整保留？
□ L1 制度定位句式原文收录（附条文编号）？
□ L1 无"幻想"内容？
□ L1 标签来自 tag-index.md？
□ L2 目标 wiki 文件已 Read 最新内容？
□ L2 任务编号/序号准确？
□ L2 牵头单位/责任单位标注？
□ L2 数据指标原文照录？
□ L3 来源文件路径正确？
□ L3 source 列表已去重？
```

## 七、强制前置读取规则 `CRITICAL`

> **设计原则**：执行任何步骤前必须先确认是否需要读取关联 schema/wiki 文件。此检查不可跳过。

| 当你需要做... | 必须先读取... | 原因 |
|-------------|-------------|------|
| 使用任何标签 | `schema/2.tag-index.md` | 标签必须来自注册表，禁止凭记忆 |
| 执行摄入（提取+存储） | `schema/3.learning-methods.md` | 提取方法和存储策略的完整规范 |
| 写入 wiki 页面 | 目标 wiki 文件（Read 最新内容） | 避免覆盖已有内容、避免重复写入 |
| 查看 frontmatter 规范 | `schema/1.frontmatter-spec.md` | YAML 格式标准 |
| 了解知识库整体结构 | `schema/0.index.md` | 目录结构和流程入口 |
| 查询操作历史 | `wiki/log.md`（用 grep 按需查询） | 避免重复操作 |
| 运行增量检测 | `python3 claude/sync-log.py` | 检测 raw 目录变化 |

## 八、日志与页面维护

### log.md 按月归档
- log.md 仅保留当月记录
- 每月1日（或月初首次操作），将上月内容移至 `wiki/log-YYYY-MM.md`
- 归档格式：保留原 `## [日期]` 标题结构

### 单页面大小限制 `GUIDELINE`
- 软上限：300 行
- 超过时：拆分为子页面，主页面保留概述 + `[[子页面]]` 链接

### index.md 自动维护
- 每次摄入后更新 index.md 的"更新时间"和统计数字
- 每次新建/删除 wiki 页面后更新对应表格

### source 去重 `IMPORTANT`
- 摄入前检查目标页面的 source 列表
- 已存在的来源不重复添加（更新位置置顶即可）

## 九、引文精度规范 `IMPORTANT`

> **设计原则**：source 追踪从文件级升级到段落级，使每一条 wiki 内容都可追溯到原文的具体位置。

### 写入 wiki 时的 source 标注格式

```
## 板块标题 `[来源: 文件名.md, 第X段]`

或（政策文件有明确条文编号时）：

## 板块标题 `[来源: 文件名.md, 第Y条]`
```

### 粒度要求
- 政策文件（有条款编号）→ 精确到条款号（如 `第12条`、`第三章第二节`）
- 一般文章 → 精确到段落范围（如 `第3-5段`）
- 会议讲话 → 精确到讲话章节（如 `第三部分 工作部署`）
- `GUIDELINE` 不要求每句话都标注，但每个板块必须有 source 标注
